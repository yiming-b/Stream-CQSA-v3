## 1. Decision summary

1. **What is built:** ONE extension (the `native/` tree = v11 + wave modes + `bwd_wave`) whose forward is v11's live-tile loop rebuilt around a host-built run table, one softmax instantiation, a masked-diagonal skip, reversed CTA order, the uniform layout + `lens[W]` as the only layout (the classic call is a W=1 wave), an outlined legacy mask path and one translation unit per (hdim, dtype, causal, mode); and whose backward gets index-based accessors, compile-time verdicts, a live-m-block loop, `numden` templated out, `deterministic` exposed and in-place wave reads.
2. **In what order:** Phase 0 Python-only, now (alignment everywhere with the census's rule, routing by memory model, async wave host merge, measurements) -> Phase 1 one experiment build (forward per-element path compiled out, backward CQS compiled out, cuobjdump, ncu) -> Phase 2 the **backward kernel first** (its live-tile path is 2.04x FA-2 and every wave backward pays it) -> Phase 3 the forward kernel, then one binary -> Phase 4 config matrix (bf16, hdim128, GQA), executor unification, planner, cost-aware multi-device scheduler + reduce_scatter, tests, release as a single extension.
3. **Largest realised gain is Python-only:** 128-aligned chunk layouts take the same v11 binary from 1.365x to 1.004x FA-2 at L~56K and from 1.036x to 0.947x at L~225K (layout_ab). On that layout masked-tile skipping is already at its floor (real = 0.78 x zero); what remains in the forward is the 21-26% all-live tax and the small-L costs.
4. **Deliberately not done:** H100 (the FA-3 port is deferred; the run table, the no-`Is_first` softmax and the 128-row block map are the three things it needs, map 5.3); in-place reads are a memory-model choice, not the default (they cost 3-6%, layout_ab); no acceptance is written against LOG.md baselines or against flash_attn ratios before the re-base (section 3.3); the 128x64 occupancy experiment runs only if ncu SourceCounters say the loop is issue-starved; no dQ-pass deterministic design.
5. Every ratio in this program is same-job, same-node (A100-SXM4-80GB), with the GPU name in the log and in the JSON row.

## 4. Kernel design (unified A100)

### 4.1 Mask/run representation and host table builder

- **Kept unchanged:** int64 group bits (one bit per non-owner chunk run, `csrc/flash_attn/flash_api.cpp:37-220`; pair masked iff `bits[r] & bits[c] != 0`, `csrc/flash_attn/src/mask.h:483-498`) and the 64-token OR/AND summaries (`stream_cqsa/interface.py:167-209`, `CQS_BLK_SIZE = 64` enforced at `flash_api.cpp:789`; verdicts `mask.h:150-176`) as the kernel-agnostic ground truth; packed per wave with prefix arrays (`native/csrc/flash_attn/src/flash.h:181-200`).
- **Added: per-row-block live-run table** `runs[m][k] = (n_lo, n_hi)` over 128-column tiles that are not fully masked, capped by the causal limit, MAXR entries per row (itr=1 causal MAXR=1, non-causal 2, itr=2 <= 3 [I, P2; confirmed by extending the census]); built in numpy at `build_tasks` time from the summaries (reference implementation: `stream_cqsa/triton_kernel.py:255-288` `live_runs`, 351-384 `live_runs_batched`), cached with the task in `build_tasks_cached` (`stream_cqsa/stable_stream.py`), packed per wave as `[W, R, MAXR]` with the stride rematerialised from `blockIdx.y` exactly as the uniform layout does for bits/summaries (`native/csrc/flash_attn/src/flash_fwd_kernel.h:109-125`). Runs are stored in **descending n** so the visit order is exactly v11's (`csrc/flash_attn/src/flash_fwd_kernel.h:461-569` visits live tiles in descending n): bit-identity is preserved by construction.
- **Specials:** causal-diagonal tiles and the ragged last tile are handled in the masking loop (4.3). Mixed tiles do not exist at align=128 (F10), so the legacy per-element path only has to be **out of the hot loop**, not fast: G5 chooses P2's outlined column-mask helper over P1's fragment-ordered 2 KB special-word tables (O(mixed tiles x 2 KB): ~50 GB at 2M for a random mask by P1's own estimate; 190 MB at L=56K for the test suite's random pattern).
- **G5 decision rule for K1:** keep P2's CTA-uniform runtime `cqs_aligned` flag (legacy align=1 tasks stay correct through the old column-summary path) **unless** P0.4(b)'s ncu SourceCounters attribute a material share of the 43% fixed-latency stalls to the search-loop loads or a loop-carried flag; in that case P1's item table (specials as their own items, plain body = FA-2 verbatim plus two CTA-uniform selects, no runtime flag) is adopted in K1. Either way the flag is removed in K2.
- **Table cost:** O(patterns x C) per task, vectorised numpy (Triton's Python-loop build is ~1 ms per call with a `.tolist()` sync, map gap 12): target <= 3 ms per 56K task, <= 60 ms for a c=73 wave at 131K under `CQSA_CPU_THREADS=8`; verified in P3.1.
- The same table gives **exact live-tile counts per row block**: the planner's cost term (5.5) and the scheduler's work curve (6).

### 4.2 KV loop

- v11's straight-line body (`csrc/flash_attn/src/flash_fwd_kernel.h:492-569`: wait/sync, V load, QK GEMM, wait/sync, K prefetch, mask, softmax, PV GEMM; no predicated regions, no `continue`) with the `while` search for the next live tile (514-521, two 16-B summary loads + compares between the QK GEMM issue and the K prefetch) replaced by `n_next = (n_block > run_lo) ? n_block - 1 : next_run_hi` from <= 6 registers loaded once per CTA (or 24 B of smem): no loads, no data-dependent loop. The in-place delta of `n_next` is looked up in the same slot (the native kernel already fetches the block-map entry during the GEMM, `native/.../flash_fwd_kernel.h:579-597`; the cut from 5% to ~2% came from that prefetch, LOG.md:1064-1067). No column-summary loads on the aligned path; the dead 1 KB `sCqsBits` smem (`csrc/flash_attn/src/flash_fwd_launch_template.h:76`, map gap 13) is removed.
- Rules the history fixed: no predicated regions and no `continue` in the steady loop (v3 +5-9%, v9 non-causal, Triton's scalar `if` +27-31% at every L: LOG.md:669-673, 842-851).
- **Reversed CTA order:** `m_block = num_m_block - 1 - blockIdx.x` (heaviest causal row blocks first). P2's simulation with real CTA lengths: 6.2% drain tail with ascending order at L=56064 (3504 CTAs on 216 slots) vs 0.1% reversed; ~0.4% either way inside a c=73 wave [I]. Free and bit-identical; an A/B arm in P3.1, not a counted gain until measured (P0.4(e) re-simulates it from the census tile counts).
- **Row-range launch:** a per-subproblem `[m_lo, m_hi)` parameter so a rank may compute a row span of a subproblem (section 6); in P3.1's build explicitly (feasibility-judge P2 E8), not "folded in later".

### 4.3 Masking-step and mixed tiles

- **Single softmax instantiation:** initialise `row_max = -INF`, `row_sum = 0`, `acc_o = 0` and call `softmax_rescale_o<Is_first=false, Check_inf=true>` on every tile (`csrc/flash_attn/src/softmax.h:136-165`). With prev = -INF, `Check_inf` maps a -INF current max to 0, `scores_scale = exp2f((-INF - cur) * s) = 0`, `row_sum = 0*0 + sum`, `acc_o = 0 * 0`: exactly the `Is_first` results; `scale_apply_exp2`'s -INF guard (softmax.h:68-90) keeps fully masked rows finite. Both proposals verified this bit-identity by reading the code [I until the maxdiff gate in P3.1 runs]. It removes the `Is_first` instantiation and the `masking_step == 0` choice (flash_fwd_kernel.h:400-411).
- **Masked-diagonal skip:** the masking loop (flash_fwd_kernel.h:361-403) today computes only `cqs_tile_clear_c`, so a fully masked diagonal tile of a non-owner row block runs the per-element `apply_mask` path (5.5-5.7x a live tile, LOG.md:468). New: compute the masked verdict too (CTA-uniform) and wrap GEMM + mask + softmax + PV in a uniform `if (!masked)`, loads/fences/barriers unconditional; this runs on <= 2 tiles per CTA, so the v3/v9 issue-efficiency lesson does not apply. Saving: 5.5 live-tile-equivalents on 2/3 of the row blocks = 1.7% at L=56K, 5.8% at L=16K (c=73), 8-10% at L=7K (P2 arithmetic [I]) -- the wave's regime (F7).
- **Ragged last tile:** predicated loads through `BlockInfo`'s `actual_seqlen` (the `!Is_even_MN` instantiation) with `col_limit` from `lens[w]`. F2c shows this instantiation costs <= 0.5%, so one lens-based instantiation serves everything; P1's forced `Is_even_MN=true` fast path is not built (G4).
- **Legacy mixed tiles** (align=1 tasks, the test suite's random/half patterns): an outlined `__noinline__ cqs_row_colmask(row_bits, col_base, tables) -> uint4` returning a 128-bit column mask for one row (from the <= 3 runs intersecting the tile, or from a 128-word smem stage for arbitrary bits); the inline hot code applies 64 bit-test + selects. **The `acc_s` fragment never crosses the call**: P1's `__noinline__ special_mask(acc_s, word, ...)` would force the 64-float fragment to local memory, which is the mis-compile signature (STACK 616-680 B, LDL, L1 hit 35%; feasibility-judge P1 E2). The per-element path (`mask.h:510-700`, instantiated in both loops, 74.8K SASS, LOG.md:671) leaves the hot loop.

### 4.4 Instantiation / translation-unit plan and ptxas retirement, with fallback

- **Today:** `CQS_MODE_SWITCH` (`csrc/flash_attn/src/flash_fwd_launch_template.h:57-72`) instantiates modes {0,1} for causal and {0,2} for non-causal inside one TU per (hdim, dtype, causal), times `is_even_MN` x `even_K` x `local` x `return_softmax` x `dropout`. The non-causal CQS-on kernel mis-compiles (F15), so production carries a second extension (`csrc_nc` = v9, `interface.py:13-47`); the hdim128 wave modes and non-causal wave mode 4 never leave ptxas. The trigger is hypothesised, never confirmed: LOG.md:704-712 blames co-instantiation in the same TU / the `Cqs_mode` template shape (v9's own code with a runtime flag mis-compiles inside v10/v11's TU); P2 blames code size. **Both are tested:** Phase 1 tests code size alone (`-DCQSA_NO_ELEMENT_PATH` on v11, per-TU ptxas time, SASS size, zero-pattern instruction count) before any rewrite; K2 tests the TU split.
- **New:** one TU per (hdim, dtype, causal, mode): 8 CQS-off TUs = upstream FA-2 unchanged (mode 0 == FA-2, `kernel_ab` `v11_plain` ~ `fa2`); 8 CQS-on TUs, each with exactly one softmax variant, one `apply_mask` variant per loop, the outlined colmask, only the `!Is_even_MN` instantiation, `Is_even_K` forced, and **no local / alibi / softcap / dropout / return_softmax** (G4: a stated capability drop; these were inherited but never tested with CQS, map gap 14, and the wave entry already rejects dropout/alibi/softcap, `native/csrc/flash_attn/flash_api.cpp:2515-2620`); `__launch_bounds__(kNThreads, kMinBlocksPerSM)` from the traits (none exists anywhere today: grep of `csrc/`, `native/`); `-lineinfo` in dev builds; `-Xptxas -v` and per-TU ptxas wall time with timestamps written to a full log (`next/kernel/build.sh:18` pipes through `tail -20` and would hide it; the `slurm/ultimate/` build script tees everything); `cuobjdump -res-usage/-sass` as build artefacts; `next/kernel/watchdog.sh` with `LIMIT=30-45` for experiments (default 90, `watchdog.sh:6`). Torch's ninja build resumes finished objects after a kill, so a hung TU costs only its own budget.
- **Fallback (mechanical, ~0.5 day):** if the non-causal hdim64 CQS-on TU still mis-compiles after K2, compile `csrc_nc`'s v9 loop as the non-causal CQS-on TU inside the same `.so` (the two trees differ only in `flash_fwd_kernel.h` and the launch template, `setup.py:238-245`): still one extension, two loop bodies to maintain. If an hdim128 wave TU still hangs, it stays gated by `Wave_ok` (`native/.../flash_fwd_kernel.h:76`) and hdim128 is served without waves. Further levers: `maxrregcount` / `__launch_bounds__` sweeps with the `-lineinfo` ncu source view.
- **Retired at the end of K2** (each preceded by a test-dependency inventory, P1's risk list): `csrc/`, `csrc_nc/`, `CQSA_CUDA_MODULE_NONCAUSAL`, `Cqs_mode` 1/2/4, the varlen wave layout, the numden runtime branch (kept as an instantiation only if a test still needs it).

### 4.5 Wave / lens layout and in-place reads

- **Uniform layout is the only forward layout:** W >= 1 subproblems padded to S = ceil(max_L/128)·128, grid (S/128, W, H), per-CTA table offsets `bidb * stride` rematerialised from `blockIdx` (the varlen wave held table pointers in registers at REG 255 and was 12% slower at W=1: 19.9 vs 17.7 ms, LOG.md:996-1013), plus `lens[W]` for the ragged tile. One instantiation then serves causal and non-causal, W=1 and W=1000, gathered and in-place, and a ragged global N. **W=1 packed = v11 gathered within 0.6% and bit-identical (F5)**, so the classic single-subproblem entry `fwd_cqs_group_bits` (`interface.py:247-296`) becomes a W=1 `fwd_wave` launch with a `[1,S,H,D] / [1,H,S]` view sliced to L.
- **Padding waste:** with aligned chunks S - L <= one 128-block plus the tail: 256 rows at 131K c=7 (0.46%), 256 at 1M (0.06%), <= 1.6% at c=73 (P2 arithmetic [I]). Census `uniS` (sum L / (tasks x max L)): 0.997 (c=7 itr=1, 131K), 0.995 (itr=2,3), 0.936 (c=31 itr=2, 131K), 0.962 (c=133 itr=1, 131K), >= 0.984 elsewhere for c=7/31; `plan_waves` groups tasks by L whenever `uniS` would fall below 0.95 (P1 M6).
- **In-place reads:** contract unchanged: align = 128, every tile size divides 128, one base row per 128-block (`cqs_block_base` / `cqs_seg_delta`, `csrc/flash_attn/src/flash_fwd_kernel.h:28-35, 156-160, 200-217`; `stream_cqsa/reference.py:583-605` `segment_block_base`; `native/.../flash_fwd_kernel.h:255-283`), batch stride 0 in the uniform layout, the next tile's delta fetched with the run-table step. `lens[]` makes in-place legal for any N and removes the `N % 128 == 0` gather with its 0·NaN hazard (`stream_cqsa/native_wave.py:491-507`). **Cost is 3-6%, not 2% (F4)**, so in-place is a memory-model choice (5.2): gather when the three packed fp16 copies fit, in-place when they do not, always in-place through the ChunkPool for host-resident inputs. At 1M c=7 the wave's 3% in-place penalty (~3% x 7 x 1.1 s = 230 ms [I]) exceeds the device gather it replaces (0.06 s per 3.1M tokens, `stream_cqsa/autoconfig.py:210-219`).

### 4.6 Epilogue contract

Unchanged: normalised fp32 out written from the MMA registers right after `normalize_softmax_lse` (`csrc/flash_attn/src/flash_fwd_kernel.h:573-601`), lse fp32 in `[W, H, S]`, `o_ptr == nullptr` skips the fp16 store (`native/.../flash_fwd_kernel.h:135-151, 646-686`). Consumers stay as they are: `wave_merge_kernel` (`native/csrc/flash_attn/src/wave_kernels.cu:28-73`, rows stably sorted by global token on the host, fixed-order fold, no atomics, bit-reproducible), `local_stats_flash` (`stream_cqsa/stable_stream.py:1038-1067`), `merge_rows_torch`. One change inside the merge: stage the (token, head) block's lse values in smem once instead of re-reading `lse_pack` per thread per entry per pass (`wave_kernels.cu:44-64`; "could be halved", LOG.md:1084-1087; 9 of 153 ms at c=73).

### 4.7 Backward design

`csrc/flash_attn/src/flash_bwd_kernel.h` is shared by the classic and the wave backward (the native copy differs by 12 lines: packed-table offsets, `native/.../flash_bwd_kernel.h:103-108`), so both engines inherit every change.

**Measured basis (F6):** zero/F 1.99-2.04 and real/F 1.89-1.93 at every L; dead-tile overhead is negative (skipping already nets ~7.5% of the 22% it could); the entire 2x is the live-tile path (live slowdown 48.87 of 88.83 ms at 56K). Phase 1's `CQSA_BWD_NO_CQS` arm (`setup.py:185-189`; `flash_bwd_kernel.h:456-470, 566`) splits it into (plain/FA-2) x (zero/plain). The Triton backward (two deterministic kernels, 7 GEMMs per live tile) beats the fused 5-GEMM CUDA kernel by 1.3x at L=56K (68.11 vs 88.50 ms, `results/triton_bwd_bench.json`), so the loss is the per-tile non-GEMM path, not GEMM work [I].

**Design (G6 = P1's addressing + P2's route rule):**

1. **Index-based accessors** `gQ(m)`, `gdO(m)`, `gLSE(m)`, `gdPsum(m)`, `dq_accum(m)` computed from `m_block` (plus a block-map delta for in-place Q/dO/lse/dpsum) replace the pointer decrements (`flash_bwd_kernel.h:682` dq_accum, 698-700 Q, 728-731 dO/O, 747-750 LSE/dPsum). Today a `continue` is illegal precisely because those decrements and the sQ/sdO double-buffer swaps carry state (501-509, "a set of guards rather than a `continue`"); with `at(m)` a dead row block is simply not visited.
2. **Compile-time verdicts:** `_c` helpers (shifts, `kCqsBlk = 64`) with the column half computed once per CTA (the CTA owns one `n_block`) and the row half of the next live `m_block` prefetched one tile ahead, replacing the two runtime-`blk_size` verdicts per tile (`cqs_tile_masked` at 509-513, `cqs_tile_clear` at 566-573; ~20 dependent integer instructions each, LOG.md:488).
3. **Live-m-block loop** over the per-column run table (transpose of the forward table with the causal limit m >= n·kBlockN/kBlockM). Dead tiles execute nothing: no `cp_async` wait + barriers, no dP_sum gather, no P/dS convert + store, no dS loop, no 32 zero `atomicAdd`s per thread (766). The one-ahead Q/dO prefetch and the sQ/sdO double buffer are re-derived on "next live m"; the dk/dv `torch.equal` gate and the ragged (`!Is_even_MN`) cases guard the off-by-one at `m_block_min`.
4. **`cqsa_numden_mode` becomes a template parameter** (runtime branch per element in the dS loop, 648-664; the engine only calls the global-lse form, `interface.py:341-397`; `bwd_wave` sets it false, `native/.../flash_api.cpp:2753`), so the dS loop is straight-line.
5. **`deterministic` exposed.** Upstream's split-buffer path is wired: `flash_bwd_launch_template.h:78-82` (`gridDimx = ceil(num_sm / (b·h))`), `flash_api.cpp:1794-1798` (`nsplits` x `dq_accum` zeros), `convert_dQ` sums the splits; `interface.py:427-440` passes `False` and `bwd_wave` hard-codes `false` (`native/.../flash_api.cpp:2751`). Both get a `deterministic` argument. **Cost caveat (both proposals' "free at W·H >= 108" is wrong as stated):** with `deterministic` the grid is `(ceil(108/(W·H)), W, H)` and each CTA walks its column blocks serially at 1 CTA/SM for the 128x128/8-warp config, so it is free only when W·H ~ k x 108 (W·H = 150 leaves a 39%-filled second round). The engine sizes waves so W·H is a multiple of ~108 when determinism is requested and `nsplits x packed_tokens x H x D_r x 4 B` fits (2x `dq_accum`, ~1.6 GB at c=7 itr=1 131K); otherwise the Triton two-kernel backward (deterministic by construction, `triton_kernel.py:477-673`) is the fallback. Default stays dq-nondeterministic within the drift band; dk/dv `torch.equal` always.
6. **In-place wave backward** through the same block map: the packed q/k/v/dout copies (4 of the 7 `H·D·itemsize` terms, `native_wave.py:261-264`) vanish; the wave backward moves to the uniform layout with per-subproblem strides (varlen retired). Target peak <= 3.0 GiB at 131K c=7 (today 4.93 vs classic 2.26, `wave_bench.json` `bwd_131k_c7`).
7. **Route rule (P2 M1):** fix the fused 5-GEMM kernel **iff** the `NO_CQS` plain backward is <= 1.25x FA-2's backward at L=56K; otherwise port the Triton two-kernel structure (dK/dV with 4 dots, dQ with 3 dots, no atomics) to CUDA (+5 days). Decided by P1.1.
8. **Occupancy A/B for the backward:** the 64x128 config (`flash_bwd_launch_template.h:181-186`, 2 CTAs/SM) vs 128x128/8 warps at 144 KB smem (1 CTA/SM, REG 255, F16), accepted under invariant 2.

Multi-device unit for the backward = (subproblem, column-block span), matching seqk-parallel CTA ownership (G7).

## 5. Engine design

### 5.1 Alignment rule (G1; replaces P2's `L >= 32·128·c` threshold)

- **`seg_align = 128` for every task at every level.** Today `stable_stream.py:1286-1301` sets `task_seg_align = 0` outside segmented/shared_chunks mode because of the "63 real tokens became 256" note, and `distributed.py:72-77, 155-159` pass `seg_align=0`; `wave_tasks` already aligns (`native_wave.py:134-139`). All three build tasks identically with `seg_align=128` and carry `seg_base` and the run table.
- **Why it is safe (F10-F12):** `build_path_state` applies `chunk_layout(cur_len, c, align)` afresh at every level on the local length (`reference.py:165`); with align=128 every chunk but c-1 is a multiple of 128 in local coordinates and chunk c-1 (the ragged tail) is always last under `sorted_gather` (`reference.py:66-110`), so by induction every full 128-block of any task at any depth is one contiguous global run. Children of an aligned parent are automatically aligned, never need re-padding, and `segment_block_base` (`ids[::128]`) is valid for them. The "63 -> 256" growth is not reproducible from the current code (census); no aligned child ever grows past its parent (F11).
- **Escalation guard:** `refine_task` only refines a task with **L_parent >= c·128** (896 tokens at c=7, 17,024 at c=133; degenerate depths per census `projected`: itr 7/4/3/2 for c=7/31/73/133 at 131K); a subproblem below c·128 tokens is never the OOM cause, so the guard loses nothing. `max_depth_for` encodes `depth <= floor(log_{c/l}(N / (c·128)))`. The child L spread stays <= 5% once L_parent >= ~20·c·128 (`projected.first_itr_where_aligned_child_may_exceed_1.05x`: c=7 at itr 4/5/6 for 131K/524K/1M; c=31 at 2/3/3; c=73 at 1/2/2; c=133 at 1/2/2); the planner's L-grouping in `plan_waves` handles the spread, the guard handles correctness.
- P2's threshold is retired: it would have left unaligned exactly the wave's regime (c=73 at N=131K: L=16K vs a 299K threshold; every c=133 task below 1.6M).
- **Effect with today's v11 (F1):** 1.365x -> 1.004x at 56K, 1.036x -> 0.947x at 225K per subproblem. The align=1 penalty varies 1.26-1.48 across paths at identical mixed% (F3): it is eliminated, not modelled. Paper tables were measured at align=1 and are re-run on one node type before being quoted next to new numbers.

### 5.2 Routing by memory model (P0.2)

- `WAVE_MIN_SUBPROBLEMS = 20` (`api.py:497, 531`) is retired: a W=1 wave costs nothing (F5), so every CUDA-capable forward with a device accumulator routes to the wave executor for any n_sub >= 1 when `native_supports(dtype, D)`; host-accumulator forwards route to the wave once P0.3's async merge lands (until then the classic engine, which is 2-12% faster there today).
- **Gather vs in-place:** gather (three packed fp16 copies, 3·H·D·itemsize per packed token) when the memory model says they fit next to the wave's fp32 partial output; in-place when they do not; always in-place through the ChunkPool for host-resident inputs. Rationale F4.
- **OOM inside a wave:** halve `max_wave_tokens` before escalating depth or retrying on the classic engine (today: classic retry only, `api.py:424-431`).
- **Backward routing:** the unified CUDA backward when P2.1's acceptance holds, else Triton (`interface.py:380-399` default today); `deterministic=True` -> wave backward with `nsplits` sized from the budget, else Triton; host-resident backward -> the classic pipeline (5.4).

### 5.3 Asynchronous wave host merge (P0.3)

`_merge_wave_to_host` (`native_wave.py:333-360`) is synchronous: device compact merge into a U-token `[U,H,D]` triple -> `non_blocking` copies to pinned slots -> `torch.cuda.synchronize` -> host fold. New: two pinned stage triples sized by the largest U of the plan, one CUDA event per wave, the host fold on a worker thread (`CQSA_CPU_THREADS = 8`, `native_wave.py:38-40`) after `event.synchronize()` while wave i+1's kernel runs -- the classic engine's `_FWD_MERGE_ASYNC` pattern (`stable_stream.py:114-117`). Acceptance: wave acc=CPU <= classic acc=CPU at 1M-2M in one interleaved job (today 9.41 vs 9.08-9.44 s at 1M; 35.41-35.76 vs 33.70-34.10 s at 2M; `results/profile_sweep/results.jsonl`); outputs equal to the synchronous path up to fp32 summation order (rel <= 1e-6). Risk: the host fold is 2.25 s per 3.1M tokens at 8 threads (`autoconfig.py:213`) against ~1.1 s of kernel per M tokens at L=449K; the overlap ratio is checked at 16K-token subproblems too.

### 5.4 The classic pinned pipeline is kept (G2; resolves P2's silent drop)

`stable_stream.py`'s per-task pipeline (pinned double-buffered staging, `shared_chunks`, escalation, `task_subset`, host or device accumulator) remains the executor for:
- **host-resident inputs' backward** with fp32 host gradient accumulators: the paper-scale backward (8.4M / 16.8M tokens, LOG.md:1265-1276) needs 3·N·H·D·4 = 50-100 GB of fp32 gradients, while the wave backward keeps dq/dk/dv resident on the device (`native_wave.py:569-571`);
- the **measured-faster O-path** (`CQSA_BWD_DPSUM=0`): the global-dpsum precompute loses 2.4x when streaming from host (256K itr=2: 3985 vs 9630 ms, `stable_stream.py:115-135`), and the wave backward always precomputes it (`native_wave.py:563-568`);
- the Triton inner kernel, and `kernel="cuda-classic"` for A/B.

Its kernel launches become W = n_par waves through the same `fwd_wave` entry (P1's "waves of n_par tasks"), so it loses the per-launch gaps without losing its features. Giving the wave executor a host-resident gradient path (and re-measuring dpsum with pinned inputs) is a separate work package outside this program. The `CQSA_SCATTER_ASYNC` contradiction (`stable_stream.py:105-113`: comment says "next/: default ON", default is `'0'`; measured neutral 0.94-1.01x, LOG.md:539-551) is resolved by keeping `'0'` and fixing the comment.

### 5.5 Planner: wave memory term and exact live-tile counts (P4.3)

- **Peak model per (itr, acc):** wave CUDA itr=1 GPU `7.149·N + 1.78·W_wave + 0.031` GiB (R^2 0.99994), itr=2 GPU `6.902·N + 1.924·W + 0.032`, itr=1 CPU `3.968·N + 2.396·W - 0.063`; classic `9.043·N` / `5.333·N` (`results/profile_sweep/fits.json` `mem_fit`). `estimate_peak_bytes` (`stable_stream.py:609`) has no wave term: add `W_tok x fwd_bytes_per_token(H, D)` (`native_wave.py:256-259`: H·D·4 + H·4 + 40 B per packed token) and make `wave_tokens` a `plan()` axis (`autoconfig.py:348-398`) chosen on the (time, memory) frontier (v2.2.1's cap `min(2M, max(512K, N))` costs <= 1.3% time, `native_wave.py:393-403`); refit after gather-vs-in-place routing (the a-term is expected to fall from 7.15 toward ~5 GiB/M when in-place is chosen [I]).
- **Cost model:** `compute = sum_tasks live_tiles(task) x t_tile(device) + R(task) x t_row + t_launch`, with `live_tiles` exact from the run table (replacing `(l-1)/l^2`, `autoconfig.py:233-236`) and `(t_tile, t_row, t_launch)` per device model fitted by `calibrate()` (`autoconfig.py:476-539`) at L = 7K/14K/28K/56K and cached per GPU key (`_gpu_key`, 273-293). Seeds: SXM4 defaults `pair_rate 7.4e11`, `kernel_ratio 1.40` (`autoconfig.py:206-207`; the ratio is now 1.00 on aligned tasks and must be refit), PCIe-40GB `pair_rate 4.98e11`, `kernel_ratio 1.30` (`results/costmodel_a100_pcie40_interactive.json`). Small-L non-linearity below 16K may need a 4th point at L=4K.
- **Acceptance:** peak prediction within 10% and time within 15% of the profile_sweep rows at 128K..2M x itr {1,2} x acc {gpu,cpu} and at c in {7,31,73,133} at 512K; `calibrate()` <= 2 min on one SXM4 and reproduces the kernel curve at L=7K..56K within 10%; `plan()` no longer references `WAVE_MIN_SUBPROBLEMS`.

## 6. Multi-device scheduler design (G7)
