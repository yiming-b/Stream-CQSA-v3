# BUG: v2.2.3 `attention(..., c=73)` returns a wrong result (every pinned c other than 7)

Found by the U1 engine A/B (`results/ultimate/engine_ab.md`, job 15958597, A100-SXM4-80GB): the `v223_cuda`
and `v223_triton` arms at N=131072, c=73, itr=1 returned rel error 1.3e+00 (output) / 1.4e+00 (gradients)
against flash_attn in 66 ms, while the c=7 rows of the same arms were correct (1.4e-4) and the v3 arms at c=73
were correct (2.1e-4, 168 ms). Diagnosed 2026-10-21 on della-vis1 (shared A100-PCIe-40GB, correctness only).

## Mechanism

`stream_cqsa.api._run` (v2.2.3, lines 372-406) builds the engine kwargs from the plan and then applies the
caller's overrides on top:

```python
kw = p.engine_kwargs() if p.mode != "mono" else dict(itr=1, c=7, interest_set=(0, 1, 3))
...
kw.update(overrides)                 # overrides = {itr: 1, c: 73, bwd_itr: 1}
```

`c` is overridden; `interest_set` is not. The plan at N=131072 on an 80 GB (or 40 GB) device is monolithic,
so `kw` starts as `(itr=1, c=7, interest_set=(0, 1, 3))` and becomes `(itr=1, c=73, interest_set=(0, 1, 3))`.
(When the plan is a decomposition the same happens with the plan's own c's set.) Logged on vis1:

```
plan: mono 0 7 (0, 1, 3)
stream_cqsa_attn kwargs: {'itr': 1, 'c': 73, 'interest_set': (0, 1, 3), 'bwd_itr': 1, ...}
stream_cqsa_forward info: n_subproblems=73, c=73, interest_set=(0, 1, 3), max_local_size=5388   # 3 x 1796 tokens
```

`(c=73, (0, 1, 3))` is not a perfect difference set: its differences cover 6 of the 72 non-zero residues
mod 73, so of the 73*72/2 off-diagonal chunk pairs only 73*3 are ever gathered into a subproblem; the
engine runs 73 subproblems of 3 chunks (5.4K tokens) instead of 9 chunks (16.2K tokens), never validates
the pair, and the max-shifted merge recomposes a result in which ~90% of the keys are missing. Hence the
signature: fast (pair work 9/73 of the monolithic call) and wrong (rel error ~1). Nothing in the plan
(info reports `classic`, itr=1, c=73, 73 subproblems), the task layout (seg_align=0 or 128), the kernel
(v11 CUDA, Triton forward, CUDA or Triton backward: all identical 1.27e+00) or the merge is at fault; the
subproblem outputs are not zero or lse=-inf, they are exact attention over the wrong key set.

v2.2.3's engine layer (`stable_stream.build_tasks`, `native_wave.wave_tasks`) accepts any `(c,
interest_set)`; the only validation is in `autoconfig.plan` on the planner's own candidates, which the
override path bypasses. c=7 is correct by accident: its set is the default.

## Reproduction (vis1, v2.2.3 snapshot, stable v11/v9 modules, python -P, same kwargs as the harness)

`attention(q, k, v, is_causal=True, kernel="cuda", return_info=True, itr=1, c=C, bwd_itr=1)`, B=1 H=8 D=64
fp16, q/k/v requiring grad, norm-relative error vs torch SDPA (flash) on the same inputs:

| c | N=131072 out / worst grad | N=65536 out / worst grad |
|---|---|---|
| 7 | 1.36e-04 / 3.57e-04 | 1.35e-04 / 3.56e-04 |
| 31 | 7.22e-01 / 7.87e-01 | 7.42e-01 / 8.09e-01 |
| 57 | 1.09e+00 / 1.18e+00 | 1.12e+00 / 1.22e+00 |
| 73 | 1.27e+00 / 1.38e+00 | 1.30e+00 / 1.42e+00 |
| 91 | 1.44e+00 / 1.57e+00 | 1.48e+00 / 1.61e+00 |
| 133 | 1.78e+00 / 1.95e+00 | 1.84e+00 / 2.00e+00 |

The error grows with c because the covered fraction of chunk pairs, ~7/c, shrinks. The harness worker itself
(`benchmarks/ultimate/engine_ab.py worker`, arm v223_cuda, N=131072, c=73) reproduces 1.265 / [1.37, 1.38,
1.27] on vis1. With `interest_set=QUORUM_SETS[c]` passed explicitly every row is correct (2.1e-04 ..
2.4e-04 / 3.5e-04), which isolates the override path. Same result with `CQSA_BACKWARD=triton`, with
`kernel="triton"`, and forward-only (`torch.no_grad`).

## Affected configurations

- Package: every release with the one-call API, v2.1.0 .. v2.2.3 (commit e6dcb30, 2026-09-13), and the v2
  `main` branch (`api.py` line 406 is the same code). The README documents `c=` as a pin on its own
  ("pin a setting ... `c=`/`interest_set=`"), so a user following it gets this.
- Call: `stream_cqsa.attention(..., c=C)` (and `patched_sdpa`/`patch_sdpa` routed calls with the same
  overrides) with `C` different from the plan's c and no explicit `interest_set=`. In practice: any pinned
  c other than 7 when the plan is monolithic or picks c=7, and any pinned c that differs from a decomposed
  plan's c. `interest_set=` passed with the matching set is correct; the automatic path (nothing pinned) is
  correct, since the planner carries `(c, interest_set)` together; `stream_cqsa_auto` / `attention_oom_safe`
  ladders change only `itr`, so they are correct.
- Every N, itr (the mismatch is per level), both engines (classic and wave: `wave_attention` takes the same
  `kw`), both layouts, every kernel and backward, forward and backward, device- or host-resident inputs.
- v3 is NOT affected through `attention()`: since commit 837e2d9 (2026-09-23, "routing by the memory
  model") a pinned `c` re-plans with `quorum_sets={c: QUORUM_SETS[c]}` (`api.py` lines 330-341), and an
  explicit mismatched `interest_set=` is rejected by the planner. Verified on vis1 with the v13 module: every
  c in QUORUM_SETS at N=131072 and 65536, itr=1, forward and backward, 1.3e-04 .. 2.3e-04 / 3.5e-04, on the
  aligned layout and on the legacy `seg_align=0` layout alike (the alignment change is not what hides it).
  v3's engine entry points (`stream_cqsa_forward`, `stream_cqsa_attn`, `wave_forward`) did still accept the
  mismatched pair and reproduced 1.27e+00 when handed it directly; they now refuse it (below).

## Fix in v3 (committed on main)

- `stream_cqsa/reference.py`: `QUORUM_SETS`, `is_perfect_difference_set` (now also rejects repeated
  members) and the new `check_quorum_set(c, interest_set)` (ValueError naming the missing differences and
  the matching set) live in the leaf module; `autoconfig` re-exports them.
- `stream_cqsa/stable_stream.py`: `build_tasks` and `refine_task` call `check_quorum_set` first, so the
  classic forward, the classic backward, the wave engine (`wave_tasks`) and the OOM refinement all refuse a
  pair that is not a perfect difference set instead of computing a wrong result.
- `tests/test_v3_quorum_sizes.py`: every c in QUORUM_SETS x N in {65536, 131072} x itr in {1, 2} through
  `attention(..., c=)` against SDPA-flash, forward and backward, decomposition asserted with
  `tests/_decomp.py`, info checked for `c**itr` subproblems and `QUORUM_SETS[c]`; the capped itr=2 rows
  (c**2 > 4096) must raise, never substitute; the engine entry points and `attention(..., c=73,
  interest_set=(0, 1, 3))` must raise. 44 tests, all passing on vis1 (2 min GPU time).

## Minimal fix for a v2.2.4 hotfix (not applied; the v2 repo is frozen)

`stream_cqsa/api.py`, `_run`, after `kw.update(overrides)`:

```python
    kw.update(overrides)
    if "c" in overrides and "interest_set" not in overrides:
        from .autoconfig import QUORUM_SETS
        try:
            kw["interest_set"] = QUORUM_SETS[int(overrides["c"])]
        except KeyError:
            raise ValueError(f"c={overrides['c']} is not a known quorum size; pass interest_set= "
                             f"(known: {sorted(QUORUM_SETS)})") from None
    from .autoconfig import is_perfect_difference_set
    if not is_perfect_difference_set(int(kw.get("c", 7)), kw.get("interest_set", (0, 1, 3))):
        raise ValueError(f"(c={kw.get('c', 7)}, interest_set={tuple(kw.get('interest_set', (0, 1, 3)))}) "
                         f"is not a perfect difference set")
```

plus the same `check_quorum_set` guard at the top of `stable_stream.build_tasks` / `refine_task` (port of
the v3 change) so the engine entry points cannot be handed the pair either. Changelog line: "attention(c=)
pinned c without its interest set; every pinned c other than the plan's returned a wrong result".
